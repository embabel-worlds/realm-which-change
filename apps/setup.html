How it works

What this page writes

Two things, both into this appliance and nowhere else. A credential you enter is sent to the appliance's own keys store, which checks it where it can and refuses a value the source rejects; it is stored encrypted and no response carries it back. A service you save becomes a WatchedService entry in this world: a namespace, an app label and a repository name.

What the checks read

Pods and the commit they run: the cluster's API lists the pods with that app label, and each pod's version label is looked up as the start of a commit id in the repository's history (RunningVersions). Logs: the log store is asked how many events it holds for the service in the last 7 days and how many carry a stack trace (LogStoreCoverage); with no log store, the pods' own logs are read (KubeLogFailures), which reach back only a few thousand lines per pod. The trace: WhatBrokeInProduction goes from each failure to the line that threw it, the commit that last changed the line, and its pull request.

What a failed check means

"No pods" means no pod in that namespace carries that app label: check the label with kubectl get pods --show-labels. "The version is not a commit" means the pods' app.kubernetes.io/version label is not the start of a commit id in the repository: build images so the label carries the commit. "No log events" means nothing is shipped under that service name. An error from a source is shown as that source's error, never as an empty result.

What the appliance did here

Each check is one query that joins sources read live with your credentials: the cluster's API, the log store, a clone of the repository and GitHub. Nothing is copied out of them, and nothing is installed in the application or the cluster.
